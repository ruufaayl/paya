Security, KYC/AML and access governance

No single person, and no machine, can move money alone

Segregation of duties

Maker ≠ checker

Ops requests, Finance approves. Enforced in the app and by a database CHECK. A refused attempt is still audited.

KYC / AML

Two officers, not one

A hold moves no money. At onboarding, machines only approve clear cases; a possible sanctions match needs two compliance officers.

Evidence

Hash-chained audit

Logins, denials, decisions, AI suggestions and chat transcript reads. Verification names the first broken row.

Access

Two-step and instant sign-out

Staff need an authenticator code; any session can be ended at once. Rate limits; a data-only database role. 30 STRIDE threats.

8 roles + a scoped applicant token · tests S6–S8, K7, K9, O6, C5 · ADR-015 to 017 · docs/architecture/10–11, 16–17

Speaker D (Kanz). One role per user makes the joiner-mover-leaver SoD conflict structurally impossible, and in Mission Control every action runs as the signed-in person. A customer asking for someone else’s transaction gets 404. Onboarding: machines approve only when every check passes; only people reject; a registry timeout is a referral, never a decision; the second-officer rule is in the service and the database. Since the review we closed four gaps: staff two-step verification and instant session revocation, durable rate limits, and a data-only database role that cannot disable the ledger guards. Residual risks we own: tokens in browser storage, no MFA recovery codes, and liveness that is basic, not certified.
